Field Manual — Build & Code

How to actually build the thing.

For teammates who've never opened a code editor before. What the words mean, how to plan before you type, and what to do when it breaks.

01

The basics — what coding actually is

Coding is giving a computer exact, step-by-step instructions in a language it understands. That's it. Here are the words you'll hear all day and what they really mean.

IDE

Think: a word processor, but for code. The app where you write, run, and test your code. Examples: VS Code, Replit, Cursor. It highlights your code and shows you errors.

Frontend

Think: the dashboard of a car. Everything the user sees and clicks — buttons, colors, pages. Built with HTML (structure), CSS (style), JavaScript (behavior).

Backend

Think: the engine under the hood. The logic running behind the scenes — processes data, makes decisions, talks to storage. Common languages: Python, JavaScript (Node.js).

Database

Think: a filing cabinet that never forgets. Where information is saved so it's still there after you close the tab or restart the app.

API

Think: a waiter taking your order to the kitchen. An API lets different programs talk to each other. Your app can use one to get weather data, process a payment, or ask an AI model for a response.

AI Model

Think: the "smart assistant" powering your app. It doesn't store your app or run your website — it just helps your app think, answer questions, or generate content when your backend asks it, through an API.

Frontend
what the user sees
⇅
Backend
the logic
↙      ↘
AI Model
the intelligence
Database
the memory

Not every app uses AI, and not every app needs a database. The backend decides when to call either one — sometimes both in the same request.

And here's what coding actually feels like, minute to minute — this loop, not one clean pass:

Write code
→
Run it
→
Something breaks
→
Fix it
→
Test again
↻ repeat

Professional developers spend most of their time in this loop, not writing perfect code the first time. If your code breaks constantly, that's not a sign you're bad at this — that's just what building something looks like.

02

Brainstorming your idea

Good hackathon ideas are small and specific — not "an app for mental health," but one clear tool for one clear person. Don't touch the keyboard until this part is done.

Round 1 — Understand the problem before the solution
  • Who exactly are we helping? Can we describe one real person, not a category?
  • What do they struggle with right now, specifically — not in general?
  • Why does this problem matter to them today, not someday?
  • How do they deal with this right now, without our tool?
  • What would have to be true for them to actually stop and use what we build?
Round 2 — Pressure-test the idea
  • Is this a real problem, or one we're inventing because it sounds impressive?
  • Would someone actually open this a second time, or just once out of curiosity?
  • Can we build a rough, working version of this in the hours we actually have?
  • Does AI make this meaningfully better — or are we bolting it on because it's an AI hackathon?
  • If we had to cut everything but one feature, which one would we protect?
  • What's the simplest version of this that would still be worth showing a judge?
Too big

"Build the next Google Classroom." No team can finish this in one day — and judges can tell when a goal was never realistic.

Right-sized

"Help a student summarize their homework reading using AI." One person, one problem, one clear feature — and it's actually finishable.

03

Plan it on paper, then scope it down

Spend 20–30 minutes planning before anyone starts typing. It saves hours later.

Sketch your screensDraw boxes on paper for each screen — what's on it, what buttons do. This is called a wireframe.
Decide what needs a backendDoes data need to be saved or shared? That needs a backend + database. A static info tool might not.
Draw how information movesUser clicks a button → what happens → what's shown back. Trace it end to end before coding.
Assign one owner per pieceSomeone owns frontend, someone owns backend/logic, someone owns the pitch — even in a small team.
MVP — Minimum Viable Product

The smallest version of your idea that actually works end to end. Not a preview of the idea — a working slice of it.

Example: AI Study Assistant

MVP: ask a question, AI answers. Done. Not MVP: login, profiles, friends, notifications, dark mode.

Split every feature into two lists
  • Must Have — the feature is broken without it. Finish these first, completely, before anything else.
  • Nice to Have — polish, extras, and ideas you'll only touch once every Must Have actually works.
04

Set up your project, step by step

This is the literal sequence — where you click, what you name things, and where each piece lives.

Create one folder on your computerDesktop or Documents, anywhere you'll find it again. Name it after your project, no spaces — ai-study-assistant, not Project 1.
Open that folder in VS CodeFile → Open Folder, select it. This becomes your one workspace for the whole day — everything you build lives inside this window.
Sort your features into frontend or backendBefore creating a single file, use the test below on each feature you listed as Must Have.
Create the folders inside VS CodeHover the file explorer on the left → the "new folder" icon → make frontend and backend. Skip backend if nothing needs saving or AI calls yet.
Create your first filesInside frontend: index.html. Inside backend, if you have one: a single server file to start.
Actually see it runningFrontend: right-click index.html in VS Code → "Open with Live Server" (or just double-click the file to open it in a browser tab), then refresh after every change. Backend: it won't run by opening the file — start it from the terminal, e.g. python server.py or node server.js.
Goes in Frontend

Ask: does it draw or display something on screen? Buttons, layout, colors, text the user reads, the input box, what shows up after clicking.

Goes in Backend

Ask: does it decide, calculate, or remember something? Talking to an AI model, checking if an answer is valid, saving or looking up data.

Try asking your AI assistant
I'm a beginner building [describe your idea] for a one-day hackathon. Based on this, what should go in my frontend vs backend, and what's a simple starter folder structure? Explain briefly why each piece goes where it does.

What that folder structure looks like once it's set up:

my-project/
├── frontend/ — everything the user sees
│ ├── index.html
│ ├── style.css
│ └── app.js
├── backend/ — logic and data handling
│ └── server.py
└── README.md — what your project does, in plain words
Three habits that save you time later
  • Name files and folders after what they do, not "test1" or "final2."
  • Leave a short comment above tricky code explaining what it's for.
  • Save your work often — don't wait until the end to check it still runs.
05

Publishing your project to GitHub

GitHub is where your code lives online so your team can share it, save versions, and judges can actually open it. Most submissions ask for a repo link — here's how to get one, continuing from the folder you just opened in VS Code.

Create a GitHub accountFree, at github.com. Do this before the event if you can — one account per person is fine.
Create a new repository ("repo") on GitHubClick "New," give it the same name as your local folder, leave it empty (no README, no .gitignore yet), and set it to Public so judges can view it.
Copy the repo's URLGitHub shows it right after you create the repo — you'll paste it into the terminal in the next step.
Push your code into it, from VS Code's terminalRun the commands below, inside the same project folder you already have open.
Add your teammates as collaboratorsRepo Settings → Collaborators — so everyone can push changes, not just one person.

Where you actually type these: open your project folder in VS Code, then press Ctrl + ` (or Terminal → New Terminal in the menu) to open a terminal panel inside the editor. That's where every command below gets typed, one at a time, followed by Enter. Using Replit instead? Look for the "Shell" tab — same idea.

One time only — connect your folder to GitHub
git initTurns this folder into a git project so it can start tracking every change you make.
git add .Stages every file in the folder — tells git "these are the changes I want to save next."
git commit -m "first version"Actually saves that snapshot, with a short message describing what's in it.
git branch -M mainNames your main line of work "main" — the standard default branch name.
git remote add origin https://github.com/your-username/your-repo.gitTells your folder where the GitHub repo lives online. Swap in the actual URL GitHub gave you in the last step — don't leave "your-username" as-is.
git push -u origin mainUploads your saved snapshot to GitHub for the first time, and links this folder to that repo from now on.
Every time you save progress after that
git add .Stages whatever you've changed since your last save.
git commit -m "..."Saves a new snapshot — write what actually changed, like "added AI response box," not "update."
git pushSends that snapshot up to GitHub, so teammates (and later, judges) can see it.

Why bother committing more than once? Each commit is a checkpoint you can return to. If a change breaks everything an hour later, you haven't lost the working version that came before it.

Keep these out of your repo
  • API keys or passwords — never commit them directly in your code.
  • Large media files or auto-generated folders (like node_modules).
  • Anything you wouldn't want a judge or stranger to see, since Public means anyone can view it.

What your README should include — this is often the first thing a judge reads.

Project name & one-line descriptionWhat it is, in a single sentence.
The problem & who it's forThe same answer from your brainstorming — say it plainly.
How to run itThe exact steps someone else would follow to get it working on their own computer.
Tech stack & AI tools usedLanguages, frameworks, and which AI model or API powers it.
Screenshot or short demo clipLets a judge see it working even if they never open the live app.
Team member namesEveryone who contributed, listed clearly.
06

Cover these jobs — however your team splits them

These aren't fixed job titles. On a team of 2–4, several people can code at once, and one person can wear more than one hat. What matters is that every job below is covered by someone — nothing falls through the cracks.

CodingBuilding features and connecting the pieces — can be split across as many teammates as are comfortable coding, working on different parts at once.
DesignShaping what the user sees — layout, colors, clarity. Often the coder handling frontend does this too.
Product directionKeeping everyone focused on the Must Haves and deciding what gets cut. Whoever's least deep in the code right now can hold this.
ResearchDigging up facts, examples, or numbers that make the pitch credible — useful for whoever isn't actively coding at a given moment.
PresentingOwning the demo script and rehearsing it. Doesn't have to be one fixed person — just needs to be someone who's confident explaining the project by 2:30.
Team check-in, every 30 minutes
  • What's working right now?
  • What's broken right now?
  • Are we still building toward the MVP, or have we drifted?
  • Do we need a mentor before we lose more time?
07

Finding and fixing bugs

A bug is just a gap between what you expected and what actually happened. Debugging is closing that gap on purpose.

Read the error message fullyIt usually names the exact file and line — don't skip past it.
Find the smallest case that breaksNarrow it down: does it break on every click, or just one specific one?
Change one thing at a timeChanging five things at once makes it impossible to know what fixed it — or what broke it further.
Explain it out loudDescribing the problem to a teammate (or a rubber duck) often reveals the fix before they even answer.
Ask a mentor if you're stuck 15+ minutesThat's what they're there for — don't burn your build window alone.
Ask yourself when something breaks
  • What did I expect to happen?
  • What actually happened instead?
  • What's the last thing I changed before it broke?
  • Did it ever work — or was it always broken this way?
  • Can I reproduce the bug on purpose, every time?
Check spelling & file names firstA huge share of bugs are typos — a missing letter or wrong filename, not a real logic error.
Restart before you dig deeperSome bugs disappear after restarting the app or the IDE — rule that out early.
Print the values you're unsure aboutIf you're not sure what a variable actually holds, print it and look.
Search it — most bugs are already solvedPaste the exact error into Google or an AI assistant before assuming it's unique to you.
Try asking your AI assistant
I expected [what should happen] but instead [what actually happened]. Here's the exact error message: [paste it]. Here's the relevant code: [paste it]. What's likely causing this, and what's the smallest fix?
08

If you're not going to finish in time

Every team hits this. What you do in the last 30–60 minutes matters more than what you didn't build.

Cut scope, not cornersDrop a Nice to Have feature entirely rather than leaving three features half-working. One solid feature beats three broken ones.
Spend what's left of your Claude credits wiselyYou've got $50 in Claude credits for the day — put what's left into getting your one core feature actually working, not polishing what already works.
It's okay to fake the unfinished partA button that leads to a static, pre-written result is fine to show — just say so honestly if a judge asks.
Record a backup before time runs outScreen-record or screenshot the last version that worked, before you touch anything else.
Show up and demo it anywayA project that's honestly 60% done and explained well usually beats one abandoned at the last minute.
Ask this with 30 minutes left
  • What's the one thing that has to work for our demo to make sense?
  • What can we cut without the story falling apart?
  • Do we have a backup if the live version doesn't cooperate?
  • Have we recorded proof of the last version that actually worked?
09

What your demo needs

Judges score communication, not just code. You get about 3 minutes — here's how to spend it across six questions, in order.

Q1 · 20 SEC

What problem?

State the problem plainly before anything else.

Q2 · 15 SEC

Who's it for?

Show the audience — make them specific, not generic.

Q3 · 20 SEC

How does AI help?

Name what the AI is actually doing in your project.

Q4 · 90 SEC

Show it working

Live demo. Don't explain it — show it. This is half your time, on purpose.

Q5 · 20 SEC

Why is it useful?

Name the real impact for the person you're helping.

Q6 · 15 SEC

What's next?

What would you build with more time?

That adds up to 3 minutes flat — practice with a timer once, so no one has to guess how long 90 seconds of demo actually feels like.

A working demo — or a backupHave a short screen recording or screenshots ready in case wifi or your app misbehaves.
One designated presenterDoesn't have to be the whole team talking — pick who leads, others jump in for questions.
Know your "why"Be ready to explain why you built it this way, not just what it does.
Practiced it out loud onceEven one run-through catches awkward transitions and missing pieces.
10

Final self-check before judging

Run through this before submitting
  • Can we explain our project in one sentence?
  • Does our demo actually run, right now, on this laptop?
  • Have we tested it the way a stranger would use it — not just the way we know to use it?
  • Do we know who our project is for, and can we say why it helps them?
  • Does everyone on the team know their part of the pitch?
